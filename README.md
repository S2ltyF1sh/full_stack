# 服务预约平台（Full Stack Project）

前后端分离的服务预约平台：客户在线浏览服务、下单预约，服务人员接单上门，管理员看板与审核。

本 README 是本项目的**规格与边界单一来源**，主要读者是项目作者与 AI 助手。写代码前先看「MVP」与「不做清单」，超出边界的改动必须先在本文档中确认，再动手。

- `frontend`：Vue 3 + Vite 前端
- `backend`：Spring Boot + JPA + MySQL 后端
- 部署：Linux + Docker Compose + Nginx

---

## 1. 目标

### 1.1 产品目标

让「找服务 → 约时间 → 上门完成 → 评价」这条链路在一个系统内闭环，替代目前靠电话/微信沟通、手工排期的做法。

衡量标准不是功能数量，而是**主链路能不能跑通并且可演示**：

1. 客户在 1 分钟内完成一次预约；
2. 服务人员能看到自己今天的单并更新状态；
3. 管理员能看到当日订单总量与待处理异常。

### 1.2 工程目标

- 先把可演示的主链路做出来，再扩展加分功能；
- 保持前后端接口约定清晰，前端只依赖 `docs` 与接口契约，不猜实现；
- 第 7 天产出可演示版本，第 14 天具备可部署形态（Docker Compose + Nginx）。

### 1.3 非目标（Non-goals）

本项目**不是**：

- 通用后台管理框架或脚手架模板（不追求可复用的中台能力）；
- 多租户 SaaS（当前只有一个运营方）；
- 支付/资金结算平台（MVP 只记录金额，不做在线收款）；
- 内容社区（评价只服务于交易决策，不做社交、关注、动态流）。

## 2. 角色

| 角色 | 是谁 | 核心诉求 | 主要入口 |
| --- | --- | --- | --- |
| 客户 | 有服务需求的普通用户 | 快速找到服务、选时间、下预约、看进度、完成后评价 | 移动端优先的客户端页面 |
| 服务人员 | 提供上门服务的人员 | 看到分配给自己的单、接单/开始/完成、少填字 | 简化的接单列表 |
| 管理员 | 平台运营方 | 管服务与人员、派单、处理异常、看当日数据 | 桌面端管理后台 |

角色与权限的边界：

- 一个账号在 MVP 中**只对应一个角色**，不做角色切换与多身份；
- 服务人员不能自行创建服务，只能接受派单或接单；
- 管理员是唯一能修改服务上下架与订单异常状态的角色。

---

## 3. 核心模块

六个模块，按依赖顺序推进：

1. **认证**：注册 / 登录 / 角色识别，登录态贯穿其余五个模块；
2. **服务**：服务的创建、上下架、价格与时长、封面；
3. **预约**：选服务 + 选时间 + 生成预约单，是主链路的中枢；
4. **订单**：预约履约后的订单状态流转（待接单 → 进行中 → 已完成 / 已取消）；
5. **评价**：订单完成后客户打分与留言，展示在服务详情；
6. **统计**：管理员的当日/近 7 日订单量、完成率、评分概览。

模块依赖关系：认证 → 服务 → 预约 → 订单 → 评价 → 统计。**不要跳过前序模块实现后序模块**。

## 4. MVP

**原则：先交付能演示的主链路，再扩展加分功能。**

| 项目边界 | 取值 |
| --- | --- |
| 核心角色 | **3** —— 客户 · 服务人员 · 管理员 |
| 核心模块 | **6** —— 认证 · 服务 · 预约 · 订单 · 评价 · 统计 |
| 计划周期 | **14 天**（第 7 天完成可演示版本） |
| 部署目标 | **Linux** —— Docker Compose + Nginx |

### 4.1 范围

MVP = 上表六个模块各做**一条主链路**，只保证能用，不追求完备。

**按 3 个核心角色划分：**

| 角色 | MVP 里做的一条链路 |
| --- | --- |
| 客户 | 注册登录 → 浏览服务 → 选时间预约 → 看订单进度 → 完成后评价 |
| 服务人员 | 登录 → 看到指派给自己的单 → 推进进行中 / 已完成 |
| 管理员 | 登录 → 建服务与人员 → 指派服务人员 → 看待办异常 → 看当日统计 |

**按 6 个核心模块划分：**

| 模块 | MVP 包含 | 验收标准 |
| --- | --- | --- |
| 认证 | 客户注册/登录；服务人员与管理员由管理员创建 | 客户能注册并登录，刷新页面登录态不丢 |
| 服务 | 管理员创建服务，客户按列表浏览、看详情 | 客户能看到至少 1 个服务并进入详情页 |
| 预约 | 客户为某服务选时间并提交预约 | 提交成功后客户能在「我的预约」看到该条 |
| 订单 | 管理员指派服务人员，订单流转进行中 → 已完成 | 状态变更后客户侧同步可见 |
| 评价 | 客户对已完成订单评 1–5 星 + 可选留言 | 评分展示在该服务详情页 |
| 统计 | 管理员看到当日订单数与完成数 | 数字与订单列表实际条数一致 |

MVP 内允许的简化（先记账，后补）：

- 账号单角色，不做角色切换；
- 派单为管理员手动指派，不做算法；
- 金额只记录，不做在线支付。

### 4.2 交付节奏（14 天）

| 节点 | 交付物 | 完成标志 |
| --- | --- | --- |
| 第 7 天 | 可演示版本 | 4.1 两张表的全部验收标准可现场演示 |
| 第 14 天 | 可部署版本 | Linux 上 `docker compose up` 一键拉起，Nginx 反代可访问 |

### 4.3 技术约束（沿用现有栈，不擅自更换）

- 前端：Vue 3 + Vite，`/api` 前缀请求后端，开发期由 Vite 代理；
- 后端：Spring Boot 2.7 + Java 8，REST 风格 JSON 接口，统一错误响应格式；
- 数据：MySQL 单库持久化，JPA 管理实体，不引入微服务、消息队列、缓存中间件；
- 部署：Docker Compose 编排前后端，Nginx 负责静态资源与反向代理，运行在 Linux。

### 4.4 主链路验收（端到端）

一次演示即按此顺序手动走一遍：

1. 客户注册 → 登录；
2. 浏览服务列表 → 进入服务详情；
3. 选择时间 → 提交预约 → 在「我的预约」看到记录；
4. 切到管理员 → 看到该预约 → 指派服务人员；
5. 服务人员 / 管理员把订单推进到「已完成」；
6. 客户对该订单提交评价；
7. 管理员统计页数字随之更新。

任一步断掉，本轮不算完成。

## 5. 不做清单（Out of Scope）

以下内容在 MVP 与 14 天周期内**明确不做**。想做请先在本文档新增条目并说明理由与工期影响。

**支付与资金**

- 在线支付、退款、分账、对账单；
- 优惠券、会员价、充值余额。

**账号与权限**

- 多角色共存账号、角色切换；
- 第三方登录（微信/支付宝/GitHub）、短信验证码登录；
- 细粒度 RBAC、组织架构、数据权限。

**预约与订单**

- 复杂排班引擎（跨门店、跨时区、轮班规则）；
- 自动派单算法、抢单大厅、订单改派审批流；
- 改期/取消的违约金与规则引擎。

**消息与通知**

- 短信/微信/邮件推送，消息中心；
- 实时通信（WebSocket 聊天、IM）。

**内容与社交**

- 服务人员的社交主页、关注、动态、分享裂变；
- 多图视频素材管理、CDN、图片处理服务。

**工程与运维**

- 微服务拆分、消息队列、Redis 缓存、搜索引擎；
- 多环境 CI/CD 流水线、灰度发布、监控告警体系、日志平台；
- 多租户、国际化多语言、移动 App 与小程序端。

**工程底线（不做 = 不允许妥协）**

- 不允许提交密钥、`.env`、`node_modules/`、`dist/`；
- 不允许跳过验证直接提交（见 VIBE-CODING.md）；
- 不允许在未更新本文档的情况下扩大 MVP 范围。

## 6. 启动

```powershell
cd frontend
npm install
npm run dev
```

```powershell
docker compose up -d mysql
cd backend
mvn spring-boot:run
```

前端默认地址：`http://localhost:5173`
后端默认地址：`http://localhost:3000`

当前后端提供健康检查 `GET /api/health`，前端首页按钮可验证前后端连通性。订单状态图见 [docs/order-state.md](./docs/order-state.md)，核心 ER 图见 [docs/core-er.md](./docs/core-er.md)。

## 7. 开发约定

### Commit 规范

本项目采用约定式提交（Conventional Commits v1.0.0），统一使用小写英文类型、可选英文范围和中文描述：

```text
<type>[optional scope][!]: <description>
```

常用示例：

```text
feat(frontend): 新增登录页面
fix(backend): 修正 CORS 预检请求失败
docs: 补充项目启动说明
build(deps): 升级依赖版本
```

提交要求：

- 类型使用 `feat`、`fix`、`docs`、`style`、`refactor`、`perf`、`test`、`build`、`ci`、`chore` 或 `revert`
- 描述使用祈使句，不加句号，首行建议不超过 50 个字符、硬上限 72 个字符
- 一次提交只做一件事；前后端独立改动尽量拆分
- 破坏性变更使用 `!` 或 `BREAKING CHANGE:` 明确标记
- 不提交 `node_modules/`、`.env`、`dist/`、`target/` 等文件

完整规则见 [docs/commit-convention.md](./docs/commit-convention.md)。

### 分支与合并

功能分支建议使用 `feat/user-login`、`fix/cors-preflight` 这类与提交类型对应的命名。合并时建议使用 Squash Merge，并由维护者按本规范整理提交信息。
